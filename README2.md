# 票务分销上架系统\-DDD最终落地设计文档

## 一、项目总览 \& 业务背景

### 1\.1 系统定位

本系统为**票务分销商品上架中台**，核心职责：对接多演出/展览供应商，将异构票务数据标准化、聚合、生成商城标准商品Product/PLU，自动/手动上架至商城货架。

**重要边界：订单、履约、核销、真实库存扣减、退款全部剥离至外部独立履约应用，本系统不处理。**

本系统所有库存仅为**前台展示库存**。

### 1\.2 两种供应商接入方式（核心业务二分）

#### 1）API 自动接入

- 数据源：供应商对外HTTP接口，原始三层结构：项目\-场次\-票档

- 数据流程：系统定时拉取 → 标准化落原始库 → 领域聚合计算 → 生成Product/PLU → 上架货架

- 库存兜底：由供应商管理真实库存，我方仅展示，不维护真实库存变更

- 聚合流程：必须走聚合规则、快照比对、自动差异下架、自动上新

#### 2）Offline 人工接入（线下供应商）

- 数据源：运营后台人工录入，**无原始场次/票档数据**

- 数据流程：运营直接录入标准 Product/PLU/班期/展示库存 → 直接上架，**完全跳过聚合流程**

- 库存兜底：**我方自主维护每日展示库存**

- 变更逻辑：无自动比对、无自动下架，所有变更、下架全部人工操作

### 1\.3 两种合作库存模式

- **共享库存**：仅API接入，多家分销商同时售卖，供应商统一兜底库存

- **买断库存**：API/OFFLINE都支持，项目独家给我方售卖


- Offline固定为：买断库存、我方履约、我方维护展示库存

### 1\.4 核心业务规则（全局不可变）

1. Product 级别拥有唯一的 **统一开售/停售时间**，所有下属PLU共用，PLU无独立售卖时间

2. PLU 只管理价格，不管理售卖时间、不管理总库存

3. 可售日期、单日库存、单日状态 全部下沉到 **班期（schedule）**维度

4. API 库存存在 ticket\_item（供应商兜底）

5. Offline 库存存在 schedule（我方自主维护）

6. API 必须聚合；Offline 禁止聚合，直接成品上架

7. 上架固定顺序：先下架失效 → 再上新/更新

## 二、完整DDD限界上下文（最终定稿、无争议）

共5个业务上下文 \+ 基础设施层，**无任何订单履约逻辑**

### 1\. 供应商接入上下文 SupplierContext

**定位**：外部数据防腐、API原始数据接入、供应商管理、POI生命周期管理

**核心实体**：Supplier、ApiProject、ApiSession、ApiTicketItem

**核心职责**

- 维护所有供应商字典（Offline是其中一个虚拟供应商）

- 定时/手动拉取供应商项目、场次、票档原始数据

- 数据清洗、标准化、去重、增量落库

- 新项目识别、自动申请POI、绑定项目与POI

- 发布原始数据变更事件，驱动聚合上架

**边界**：只处理原始数据，不聚合、不上架、不碰Offline数据

### 2\. API商品聚合上下文 ProductAggContext

**定位**：仅服务API项目，纯计算域，无RPC、无外部调用

**核心实体**：ApiProduct、ApiPlu

**核心职责**

- 根据原始项目/场次/票档聚合生成标准商品、PLU、可售日期集合

- 执行快照比对，识别新增/更新/失效PLU

- 输出变更清单（下架清单、上新清单）

- 承载所有聚合规则：同开售时间合并PLU、优惠票独立商品等

- 支持定时聚合、运营手动触发聚合

**边界**：完全不处理Offline业务

### 3\. Offline商品管理上下文 OfflineProductContext

**定位**：纯人工维护域，管理线下录入的全套商品、PLU、班期、展示库存

**核心实体**：OfflineProduct、OfflinePlu、OfflineSchedule

**核心职责**

- 运营后台维护Offline商品（统一售卖时间、商品信息）

- 维护Offline PLU、PLU定价、状态

- 维护PLU下所有班期日期、单日展示库存、单日班期状态

- 数据合法性校验、唯一约束校验

**边界**：只维护数据，不聚合、不自动上架，上架由发布域执行

### 4\. 货架发布上下文 PublishContext

**定位**：统一执行层，API/Offline 两条链路共用的唯一上架出口

**核心实体**：PublishRecord、PublishItem

**核心职责**

- 统一编排上架流程：先下后上、逐PLU同步状态

- 封装商城RPC：上架、下架、价格同步、库存同步、班期同步、开关售

- 支持三种触发：定时、Binlog、运营后台手动上架

- API链路：消费聚合结果

- Offline链路：直接读取成品商品PLU班期库存发布

- 记录完整发布流水、明细、成功失败状态

### 5\. 运营视图后台上下文 AdminViewContext

**定位**：薄视图层，无业务规则，仅查询、权限、操作日志、外部数据展示与 Offline 履约信息中转（接收运营上传并转发给订单履约应用，自身不做履约业务）

**核心职责**

- 全量后台数据查询：供应商、项目、商品、PLU、班期、发布记录

- 提供所有手动操作入口：手动同步、手动聚合、手动上架/下架

- 权限控制、操作日志记录

- 远程调用外部【订单履约应用】接口，回显订单、履约记录（仅展示，不落地、不处理）

- **Offline 履约信息手动录入上传**：API 供应商可自动生成核销码；Offline 无法自动生成核销码，需运营在后台手动上传履约信息（一般以 Excel 上传，内含大量订单核销/取票信息），上传后由外部订单履约应用处理

### 基础设施层（非领域）

定时Job、Binlog监听、后台手动触发器；只发事件，无业务逻辑、无编排

## 三、最终定稿表结构（完整版、编码直接使用）

### 3\.1 公共基础表

#### supplier 供应商表

存储所有API供应商 \+ 一条固定OFFLINE虚拟供应商

### 3\.2 API链路表（完全冻结，不再修改）

- api\_project 供应商原始项目

- api\_session 供应商原始场次

- api\_ticket\_item 供应商原始票档（库存存在这里，供应商兜底）

- api\_product 聚合生成商品

- api\_plu 聚合生成PLU

### 3\.3 Offline链路表（最终定稿三层结构）

**结构：Product → PLU → Schedule（带库存）**

#### 1）offline\_product 离线商品表

存储商品统一售卖时间，整商品唯一销售窗口

- product\_uuid

- supplier\_project\_id

- poi\_id

- product\_name

- product\_status

- sale\_start\_time（商品级统一开售）

- sale\_end\_time（商品级统一停售）

- create\_time、update\_time

#### 2）offline\_plu 离线PLU表

仅存价格、状态，无时间、无库存

- plu\_uuid

- product\_uuid

- price

- plu\_status

- create\_time、update\_time

#### 3）offline\_schedule 离线班期库存表（核心）

**全系统唯一我方自主管理库存的表**

维度：PLU \+ 单日日期 = 唯一可售单元，携带单日展示库存

- plu\_uuid

- schedule\_date

- stock\_show\_num（我方维护展示库存）

- status（班期可售/停售）

- create\_time、update\_time

- 唯一键：uk\(plu\_uuid, schedule\_date\)

### 3\.4 全局上架流水表（共用）

- publish\_record 上架主任务记录

- publish\_item 单PLU变更明细记录

## 四、两条核心链路最终流程（编码必须严格遵守）

### 4\.1 API接入完整链路

定时拉取原始数据 → 落库 → 触发聚合 → 快照差异比对 → 生成变更清单 → 先下架失效PLU → 上新/更新PLU → 同步价格/班期/状态 → 记录发布流水

### 4\.2 Offline接入完整链路

运营后台录入Product \-\> 录入PLU价格 \-\> 录入每日班期\+每日库存 \-\> 手动触发上架 \-\> 直接组装数据发布到货架

**无聚合、无快照比对、无自动下架，全部人工驱动**

---

## 五、系统绝对边界（编码红线）

1. 本系统 **0订单、0履约、0真实库存扣减**

2. 所有库存分为：API供应商库存、Offline我方展示库存

3. API链路必须聚合，Offline链路禁止聚合

4. Product统一售卖时间，PLU无售卖时间，库存归属于班期

5. 后台仅视图展示订单履约数据 \+ 中转 Offline 履约信息上传（Excel），**不做任何履约业务处理**；API 自动核销码、Offline 履约录入后的实际核销与状态流转全部在订单履约应用

6. POI 统一在供应商接入层创建，不在聚合层创建

7. 领域服务严格二分：聚合计算服务、发布执行服务，职责彻底解耦
